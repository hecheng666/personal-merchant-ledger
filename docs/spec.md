# 项目规格书 v2：零售店微信经营对账器

> 更新时间：2026-11-11
> 场景：家里开零售店，个人微信收款（柜台码 + 加好友转账两种都有），现金占一部分，靠翻微信记录记账，转账截图多
> 规模：月收款几千到几万笔
> 交付形态：微信小程序

---

## 0. 方案取舍

| 你提供的信息 | 对方案的影响 |
|---|---|
| **两种收款方式都有**（柜台码 + 加好友转账） | 分类规则要分两路：柜台码 → 交易类型为「二维码收款」，可 100% 自动判定为营业；转账 → 必须走「待确认 + 记忆」 |
| **没有赊账** | 直接删掉原赊账模块，**省下约一周工作量**，全部投入核心链路和小程序 |
| **月几千到几万笔** | 两个设计必须改：① 「待确认」不能逐笔列出，要按对手方聚合；② 截图不能全量识别，只对特定子集做 |
| **现金有一部分** | 新增「现金补录」模块。现金不在微信账单里，不补录就算不出真实营业额 |
| **用小程序交付** | 可行，但有两个硬约束：ICP 备案需 7–15 个工作日；数据量决定架构必须是云端而非纯端侧 |

---

## 1. 一句话价值

把微信导出的账单 + 每天一笔现金数字，变成一张「这个月生意收了多少、花了多少、有没有哪笔没收着」的表——并且自动把混在里面的私人转账剔出去。

---

## 2. 为什么不是第 N 个烂大街项目

GitHub 上同类项目至少 5 个（小遥账单助手、payment_record_analysis、wechatpay、personal-finance-cn、double-entry-generator），**全部服务「个人想知道自己花了多少」**，没有一个服务「开店的人想知道生意赚没赚」。

差别在三个地方：

| | 个人消费分析 | 本方案 |
|---|---|---|
| 最大障碍 | 商户名看不懂 | 生意款与私人款混在一个微信里 |
| 必须处理 | 分类占比、趋势图 | 退款、抹零、提现、拆单、**现金** |
| 失败代价 | 图表不准 | 钱少了不知道 |

行业文章里的原话（可作为需求证据）：

> 「很多人以为点开『微信收款小账本』就万事大吉，结果月底对账时才发现漏洞百出。」

> 「对账时要特别留意『顾客未支付成功但以为付了』的情况。微信的语音播报不是百分百可靠，网络卡顿时会延迟甚至漏播。」

---

## 3. 数据来源：微信侧能拿到什么（已核实）

**导出路径**：`我 → 服务 → 钱包 → 账单 → 右上角「…」→ 常见问题 → 下载账单 → 用于个人对账`
→ CSV，最长一年，发到邮箱，解压密码为微信后六位

**CSV 字段**：交易时间、交易类型、交易对方、商品、收/支、金额(元)、支付方式、当前状态、交易单号、商户单号、备注

**两条收款路径在账单里是可区分的**（这是自动分类的地基）：

| 收款方式 | 账单里的「交易类型」 | 能否自动判定 |
|---|---|---|
| 柜台收款码（顾客扫你） | 二维码收款 | 可以，100% 营业 |
| 加好友后转账 | 转账 | 不行，可能是顾客、亲友、退货返款 → 待确认 |
| 群收款 | 群收款 | 可以，营业（若用于经营） |
| 红包 / 亲属卡 / 零钱提现 / 理财通 / 信用卡还款 | 对应类型 | 一律非经营 |

**解析必踩的坑**（工程量与面试细节都在这）：
1. 表头**不在第一行**，前面有说明文字
2. 文件带 **UTF-8 BOM**
3. 金额列名可能是 `金额(元)` 或全角 `金额（元）`
4. 「当前状态」有 `支付成功 / 已全额退款 / 已关闭`，**后两者必须剔除**，否则营业额虚高
5. 一笔交易可能因退款拆成两行

## 4. 数据量带来的三个设计约束（关键）

月几千到几万笔，意味着一年 3 万–30 万行。这直接否掉了几个想当然的做法：

| 环节 | 直觉做法 | 实际约束 | 结论 |
|---|---|---|---|
| 解析 | 手机端一次解析全年 | 内存与耗时都扛不住 | **按月导入**，一次一个月 |
| 存储 | 存小程序本地 Storage | 上限 10MB，几个月就爆 | 必须云端（云开发或自建） |
| **待确认** | 把不确定的交易逐条列出 | 几万笔里可能几千条，用户直接放弃 | **按「对手方」聚合**，一个陌生昵称只问一次 |
| 截图识别 | 每笔都配一张截图 | 几万笔不可能有这么多截图，OCR 成本爆炸 | 只对「待确认的转账」和「大额」做 |

**其中「待确认按对手方聚合」是整个产品的关键设计。**

因为柜台码占绝大多数且能自动判定，真正需要人工判断的只有「转账」这一小撮，而这些转账又集中在少数对手方身上。所以实际待确认清单是**几十个昵称**，不是几千笔交易。第一次点「这是顾客」，以后这个人所有转账自动归类——**越用越省事，这才是它能活下来的原因**。

## 5. 功能定义

### M0｜账单解析 + 三态分类 + 经营月报（核心，第 1–2 周）

输入：微信账单 CSV（按月）

输出：

| 输出 | 内容 |
|---|---|
| 营业收款 | 二维码收款 + 群收款 + 已确认的转账，按日汇总 |
| 进货支出 | 与已登记供货商的转账支出 |
| 私人往来 | 红包、亲属卡、提现、理财通、信用卡还款等 |
| **待确认** | **按对手方聚合**的清单：昵称、笔数、金额（收入与支出分开）、首次出现时间；一点即归类，并写入记忆库 |

**记忆库**：云端数据库（或端侧 Storage），记录「对手方 → 归类」映射，命中即自动。

### M1｜现金补录（必做，但极轻）

现金不进微信账单，不补就永远算不出真实营业额。

设计原则：**一天只输一个数字**。
- 打烊时打开小程序，输入「今天现金 380」，保存
- 报表里：营业额 = 微信营业收款 + 现金补录
- 允许补录历史日期（老板经常忘，追补三天很正常）
- 不做：分笔记录现金、商品明细、找零计算

**为什么必须按天**：按月底补一个总数，老板一定记不准，数字会变成猜的。

### M2｜截图交叉验证（第 3 周，范围受限）

只对两个子集做，不做全量：
1. 「待确认」里的大额转账
2. 单笔超过阈值的转账（如 ≥ 200 元）

处理：视觉模型抽取截图里的**金额、对方昵称、时间** → 与账单条目做带容差的模糊匹配。

输出三种结果：
- 匹配上 → 标记「有凭证」，辅助分类
- **截图有、账单没有 → 高危：疑似未到账**（语音播报漏播丢掉的钱就在这里）
- 账单有、截图没有 → 低危，仅提示未存证

### 明确不做

赊账往来（你确认没有）、报税、发票查验、多店铺、员工分账、商品库存、预算管理、消费画像。

## 6. 小程序方案（已核实可行性）

### 6.1 类目与主体：可行

微信开放社区官方回复：**【工具-记账】类目暂无资质要求，用户选择即可通过。**

而「工具-记账」的官方释义正是「适用于提供价格记录、生活开销等模板功能的记账工具」——我们的功能落在这一类里。

**个人主体的硬限制（必须避开）**：
- 不能开通微信支付（我们不需要）
- 不能做微信认证（不影响 wx.login 取 openid）
- 不能选金融、电商、医疗类目
- **文案禁区**：不要出现「发票」「报税」「税务」「财务代理」，否则会被往受限类目归

### 6.2 备案：7–15 个工作日，必须先启动

小程序上线前必须完成 ICP 备案，个人主体同样可以备，管局审核一般 7–15 个工作日。

**这是整个项目唯一的不可压缩等待期。** 所以顺序要调整：**第一周就去注册小程序主体 + 提交备案**，代码同时在本地开发，等备案下来直接提审。否则功能做完了卡在备案上，面试时拿不出可扫码的成果。

### 6.3 文件入口：这条路径是关键

`wx.chooseMessageFile`（基础库 2.5.0+）可以从**微信会话**里选文件：

```js
wx.chooseMessageFile({
  count: 1,
  type: 'file',
  extension: ['csv'],
  success(res) {
    // res.tempFiles[0].path → 读取或上传
  }
})
```

这意味着老板的操作路径是：

> 邮箱收到账单 → 转发到「文件传输助手」→ 打开小程序 → 选文件 → 出报表

**不用装 App、不用连电脑、不用找数据线**。这条路径本身就是产品价值。

注意：只能从微信会话选，不能选系统文件管理器或相册；临时路径有时效，要立刻读取或上传。

### 6.4 架构选择

| 方案 | 隐私 | 存储上限 | 实现难度 | 结论 |
|---|---|---|---|---|
| A 纯端侧（读文件 + 本地解析 + Storage） | 最好 | 10MB，几个月就满 | 低 | 只适合做 demo |
| B 云开发（上传 → 云函数解析 → 云数据库） | 数据上云 | 够用 | 中 | **推荐** |
| C 自建后端（FastAPI + 服务器） | 可控 | 够用 | 中高 | 想练后端就选这个 |

**推荐 B**，理由：个人主体可用、免运维、有免费额度、云函数天然适合「按月导入一次」这种低频任务。如果目标是练后端能力，选 C 并作为技术选型依据。

**隐私要说清楚**：账单是敏感数据。做法是——上传后只在云端保留结构化结果，原始 CSV 解析完即删；提供「清空我的数据」按钮；README 明示数据流向。

### 6.5 审核时会踩的坑（来自真实开发者复盘）

- 云函数请求体有 **约 256KB 上限**，大文件不能走 callFunction，要用云存储 + 云函数读文件
- CSV 导入必须做：BOM 兼容、文件大小与行数上限（建议 5MB / 5 万行）、格式不符单独跳过并提示、**导入前弹预览**（文件数、解析条数、新增/跳过/异常条数）
- **宁缺勿错**：解析可疑的宁可标「未识别」让用户确认，也不写进账里

## 7. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 小程序 | 原生 WXML/WXSS/JS 或 Taro | 原生最稳；Taro 便于复用 React 经验 |
| 后端 | 云开发云函数（或 FastAPI） | 解析逻辑放后端，小程序只做交互 |
| 解析 | Python 或 Node.js + 自写容错解析器 | **不要用固定 header=0**，先扫描定位真实表头 |
| 分类 | 规则引擎 + 对手方记忆库 | 规则优先，记忆兜底 |
| 存储 | 云数据库 / SQLite | 按月分表，避免单表过大 |
| 图表 | ECharts for 小程序（ec-canvas） | 日报/月报趋势 |
| 截图抽取 | 视觉模型 API | 只抽金额、昵称、时间三要素 |

## 8. 四周计划

**第 1 周｜先把备案送出去，同时打通解析**

| 天 | 任务 |
|---|---|
| D1 | 注册小程序个人主体 + **提交 ICP 备案**（立刻做，等 7–15 天） |
| D2 | 导出真实账单 CSV（近 3 个月），手工标注前 100 笔的三态答案作为标准答案 |
| D3 | 容错解析器：定位表头、清 BOM、统一列名、剔除退款与关闭 |
| D4 | 交易类型映射 + 三态分类（规则版），跑分 |
| D5 | 待确认按对手方聚合 + 记忆库 |
| D6 | 输出月报（Excel/JSON），数字与手算核对 |
| D7 | CLI 或本地 Web 版跑通，用亲友真实数据验证一次 |

**第 2 周｜核心功能完整闭环**

- 现金补录（一天一个数字 + 历史补录）
- 日报/月报聚合，营业额 = 微信 + 现金
- 后端接口（导入 / 分类 / 确认 / 报表）
- 单测：解析异常用例、退款剔除、对手方聚合

**第 3 周｜小程序前端**

- 微信登录、文件选择（chooseMessageFile）、导入预览
- 待确认清单交互（一点归类，即时生效）
- 日报月报页 + 图表
- 现金补录入口

**第 4 周｜截图验证 + 提审 + 包装**

- 截图交叉验证（限大额与待确认项）
- 备案通过后提审、发布
- README（真实截图、架构图、数据流向说明）、部署文档、复盘文章

## 9. 验收标准

- [ ] 3 份真实账单（不同月份）解析成功，**行数与微信原始记录一致**
- [ ] 退款与已关闭交易**不进入**营业额（专门写用例验证）
- [ ] 100 笔人工标注样本，三态分类准确率 ≥ 90%
- [ ] 所有不确定项进入「待确认」，**没有一笔被猜**
- [ ] 待确认清单按对手方聚合后，条目数 **< 50**（而不是几千）
- [ ] 同一对手方第二次出现自动归类
- [ ] 现金补录 3 天，月报营业额 = 微信 + 现金，且能被手算复核
- [ ] 单月 3 万行账单导入耗时 < 30 秒
- [ ] 小程序可扫码使用，备案通过，提交审核
- [ ] 提供「清空我的数据」，README 写明数据流向

## 11. 三个必须现在就处理的风险

1. **备案是唯一不可压缩的等待期**（7–15 工作日）。今天不提交，第 4 周就拿不出可扫码的成果。
2. **账单数据上云有隐私顾虑**。必须在 README 和产品里都写清楚：原始文件解析后即删、只留结构化结果、可一键清空。
3. **不要用「发票」「报税」「税务」这些词**。个人主体类目会被卡，功能也确实不涉及，没必要给自己找麻烦。
