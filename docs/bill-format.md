# 微信支付账单格式说明（基于真实样例实测）

> 本文档所有结论均来自 `fixtures/wechat-sample-real.csv` 的实测，不是推测。
> 该样例取自开源项目 `deb-sig/double-entry-generator` 的测试数据，是**专门构造的对抗性样本**，覆盖了大量真实场景的异常。

---

## 1. 文件整体结构

```
第 1 行      微信支付账单明细,,,,,,,,,,              ← 标题
第 2 行      微信昵称：[测试],,,,,,,,,,
第 3 行      起始时间：[...] 终止时间：[...],,,,,,,,,,
第 4 行      导出类型：[全部],,,,,,,,,,
第 5 行      导出时间：[...],,,,,,,,,,
第 6 行      ,,,,,,,,,,                              ← 空行
第 7 行      共43笔记录,,,,,,,,,,
第 8 行      收入：1笔 0.35元,,,,,,,,,,
第 9 行      支出：1笔 28.16元,,,,,,,,,,
第 10 行     中性交易：0笔 0.00元,,,,,,,,,,
第 11–14 行  注： + 三条说明
第 15 行     ,,,,,,,,,,
第 16 行     ----------------------微信支付账单明细列表--------------------,,,,,,,,,,
第 17 行     交易时间,交易类型,...                    ← 这才是真正的表头
第 18 行起   数据行
```

**结论：表头固定在第 17 行（0-based 索引 16），但不要硬编码。**

正确做法是扫描前 N 行，找「第一列等于 `交易时间` 且列数 ≥ 6」的那一行作为表头。微信历史上调整过说明文字的行数，硬编码 16 会在某次版本更新后全线崩溃。

> 实测：该样例共 44 行，表头 0-based 索引 = 16，数据行 = 27 行。
> 注意文件头自称「共43笔记录」，与实际 27 行不符——**不要相信摘要行，只信数据行**。

## 2. 字段定义（11 列）

| 序号 | 列名 | 实测样例 | 坑 |
|---|---|---|---|
| 0 | 交易时间 | `2019-09-26 12:45:27` | 固定格式，但行序**不保证有序**（样例里 2019、2021、2017、2024 混排） |
| 1 | 交易类型 | `商户消费` / `二维码收款` / `deg-不认识的-txType` | **近 20 种，且会出现未知值**，必须容错 |
| 2 | 交易对方 | `云膳过桥米线(传奇广场店)` / `/` | 中性交易会写 `/`，不能当昵称 |
| 3 | 商品 | `总共消费:28.16` / `/` | 格式极不统一，含「收款方备注:」「转账备注:」前缀 |
| 4 | 收/支 | `支出` / `收入` / `/` | **三态**，`/` 表示中性交易（提现、充值、理财） |
| 5 | 金额(元) | `¥28.16` / `¥50.0` | **带 ¥ 前缀**；小数位不统一（`¥50.0` 只有一位） |
| 6 | 支付方式 | `中国银行(1234)` / `零钱` / `/` | — |
| 7 | 当前状态 | `支付成功` / `已全额退款` / `提现已到账` | **9 种取值**，退款判定依赖它 |
| 8 | 交易单号 | `3985734\t` | **字段尾部带 TAB 字符**，实测 33 个字段含 TAB，必须 strip |
| 9 | 商户单号 | `129847129\t` / `/` | 同上 |
| 10 | 备注 | `服务费¥0.10` / `/` | 手续费藏在备注里，见第 5 节 |

## 3. 交易类型全表（样例中出现的 18 种）

### 经营性收入（可自动判定为「营业收款」）

| 交易类型 | 笔数 | 判定 |
|---|---|---|
| `二维码收款` | 1 | ✅ 营业（顾客扫柜台码） |
| `群收款` | — | ✅ 营业（若用于经营） |

> `赞赏码` 要看方向：**收入**方向是别人打赏你（营业款），**支出**方向是你打赏别人（私人）。
> 样例里那一笔是支出 ¥36.99 打赏 YingDev，归私人往来。

### 需人工确认（进入「待确认」，按对手方聚合）

| 交易类型 | 笔数 | 为什么不能猜 |
|---|---|---|
| `转账` | 1 | 可能是顾客付款、亲友转钱、退货返款 |

### 经营性支出

| 交易类型 | 笔数 | 判定 |
|---|---|---|
| `商户消费` | 5 | ❌ 非营业（这是花钱，进货可能藏在这里） |
| `扫二维码付款` | 3 | ❌ 非营业（付给别人的钱） |

### 中性交易（不进营业额，也不进支出）

| 交易类型 | 笔数 |
|---|---|
| `零钱提现` | 3 |
| `零钱充值` | 1 |
| `转入零钱通-来自零钱` / `-来自工商银行(9876)` | 2 |
| `零钱通转出-到零钱` / `-到工商银行(9876)` | 2 |
| `购买理财通` | 2 |
| `信用卡还款` | 1 |
| `分分捐` | 1 |
| `其他` | 1 |

**注意**：`转入零钱通-来自XXX` 这类类型名带着**银行名后缀**，同一个语义有多种字面量。判定必须用前缀匹配（`startswith('转入零钱通')`），不能用等值匹配。

### 未知类型（必须容错）

样例里有一条 `deg-不认识的-txType`，这是故意构造的。

**处理原则**：未知类型不能直接丢弃，也不能猜。应归入「未识别」桶，在报表里显示「有 N 笔未知类型未计入，请检查」，让用户自己判断。丢一笔可能就是丢一笔钱。

## 4. 退款的正确判定（最容易出错的地方）

`当前状态` 实测有 9 种取值：

```
支付成功 / 已存入零钱 / 已转账 / 朋友已收钱 / 已收钱
提现已到账 / 充值完成 / 充值成功 / 已到账
```

真实账单里还会出现 `已全额退款`、`已退款`、`已关闭`、`对方已退还`。

**规则**：

- 状态含「退款」「退还」「已关闭」→ **该笔不计入营业额**
- 部分退款会**多出一行**记录（原交易 + 退款行），不是修改原行
- 因此：营业额 = Σ(收入且状态正常) − Σ(退款行金额)

**这是最容易写错、也最容易让数字虚高的地方。必须写专门的测试用例。**

## 5. 手续费藏在备注里

实测样例：

| 交易类型 | 金额 | 备注 |
|---|---|---|
| `零钱提现` | `¥100.10` | `服务费¥0.10` |
| `零钱提现` | `¥10.10` | `服务费¥0.10` |
| `零钱提现` | `¥1001.10` | `服务费¥1.00` |

也就是说，提现 100 元，账面显示 100.10，其中 0.10 是手续费。

**对营业额的影响**：提现是中性交易，本身不入账。但如果你要算「实际到手多少钱」，必须从备注里正则抠出 `服务费¥([\d.]+)`。

这是一个典型的「金额永远差一点点对不上」的来源，值得在 README 里写一句。

## 6. 编码与格式

| 项 | 实测 | 处理 |
|---|---|---|
| 编码 | UTF-8 | 支付宝账单是 GBK，以后要多源必须区分 |
| BOM | **本样例无 BOM**，但真实导出的文件**可能有** | 统一用 `utf-8-sig` 读取，两种情况都兼容 |
| 换行 | LF（`\n`） | Windows 打开可能变 CRLF，用 `newline=''` |
| 引号 | 含逗号的字段被 `"` 包裹 | 必须用 `csv` 模块，不能 `split(',')` |
| TAB | 33 个字段末尾带 `\t` | 每个字段都要 `.strip()`，含 `\t` |

## 7.1 xlsx 入口（2026-11 新增）

部分导出入口（收款小账本、商户后台）直接给 xlsx，不是 CSV。处理方式：

1. 小程序端不解析，按 base64 读取整个文件，`POST /api/import` 传 `content_base64`
2. 后端识别 `PK` 头 → `app/wechat/xlsx.py` 用 openpyxl 读出所有行
3. 按表头别名归并成标准 11 列（如「时间」→交易时间、「金额」→金额(元)），再交给 `parse_bill_text`
4. 至少需要「时间、收/支、金额」三列，否则报错并回显识别到的表头，方便补别名
5. 加密 zip 不能直接导入，先解压；旧版 `.xls` 不支持，需另存为 `.xlsx`

分类规则、统计口径完全复用 CSV 通路，不存在第二套逻辑。

## 8. 实现清单（照这个顺序写，不会返工）

1. 读文件：`utf-8-sig`，`csv.reader`，保留原始行
2. 定位表头：扫前 30 行，找第一列 == `交易时间`
3. 逐行 strip（含 `\t`），跳过空行与列数不足的行（**记下跳过了几行**）
4. 金额清洗：去掉 `¥`、`,`、空格 → `Decimal`（**不要用 float**，钱不能有精度误差）
5. 时间解析：`%Y-%m-%d %H:%M:%S`
6. 状态判定：退款/关闭 → 标记为 `excluded`
7. 类型映射：前缀匹配 → 经营收入 / 经营支出 / 中性 / 待确认 / 未识别
8. 备注解析：正则抠 `服务费`
9. 输出：结构化结果 + **解析统计**（总行数、成功、跳过、未识别、退款、各类计数）

第 9 步的解析统计是产品的一部分：用户看到「43 行里成功解析 42 行，1 行未识别」，才会信任这份账。
